# iris3d

A scriptable 3D visualisation suite for scientific data — volumes, point clouds,
meshes, and molecular structures — built on [Bevy](https://bevyengine.org/).

iris3d runs as a desktop application and is driven over gRPC. It is not a
library you import and not a headless renderer you call: it opens a window,
holds a scene, and waits to be told what to put in it. Any language that speaks
gRPC can drive it; Python is the first wrapper, in `libraries/python`.

## Quick start

Build and run the application. It opens a window and listens on `[::1]:50051`:

```bash
cargo run
```

Then, from another terminal, drive it from Python:

```bash
cd libraries/python && uv run gallery_demo.py
```

`gallery_demo.py` builds a scene using every filter and actor kind the server
has, from one cryo-EM structure. It is the fastest way to see what iris3d can
currently draw. `density_demo.py`, `cartoon_demo.py` and `watch_demo.py` are
narrower.

To check what was drawn without looking at a window:

```bash
cargo run -- --screenshot out.png --screenshot-after 240
```

## How it fits together

The wire contract in [`proto/iris3d/v1/scene.proto`](proto/iris3d/v1/scene.proto)
is the real interface, and it is worth reading first — its header explains the
data model at length, including why data, objects and actors are three separate
things.

The short version:

- **Data** is arrays, held flat and referred to by handle. An array belongs to
  no object. One array can feed several representations.
- An **object** is a place in the scene tree and a name. It holds no data.
- An **actor** is one way of drawing something. It binds the arrays it reads to
  the inputs its kind declares, and it is drawn under the objects it is placed
  under.
- A **filter** derives arrays from arrays. It draws nothing. Narrowing a
  selection, extracting a contour, building a ribbon and mapping values to
  colours are all filters.

Filters exist so that generating geometry and displaying it stay separate: with
`N` ways of generating and `M` ways of displaying, you write `N + M` things
rather than `N * M`.

## The Rust application

One binary crate, composed of Bevy plugins wired together in
[`src/main.rs`](src/main.rs). Every module carries a `//!` header explaining
what it is for.

The modules are layered: each may only name the ones above it in this table.
Nothing in the compiler enforces that, so
[`scripts/check-layering.sh`](scripts/check-layering.sh) does, and CI runs it on
every push. It is a grep over `crate::` imports and it fails the build on an
upward dependency.

| Module | What it holds |
|---|---|
| `bus/`, `counter/`, `redraw/` | The command channel, handle allocation, the redraw policy |
| `data/` | Arrays, dtypes, the data store, the periodic table |
| `model/` | Declared parameters, bindings, and the ways a request can be refused |
| `scene/` | The scene tree, the actor registry, scene commands |
| `filter/` | Filter kinds — `cartoon`, `contour`, `colormap`, `geometry`, `select`, … |
| `draw/` | Rendering backends. `draw/default/` is the only pathway |
| `view/` | The egui panel, the node graph, camera, picking, overlays |
| `grpc/` | The tonic server. An adapter onto the command buses and nothing more |

`main.rs` adds the plugins in order and is the one place allowed to name every
layer; `cli.rs` parses the command line and `capture.rs` writes screenshots.

Work flows one way. A client sends a request, `grpc` turns it into a
`SceneCommand` or a `FilterCommand`, the owning module drains its queue and
applies it, `filter` derives whatever is now stale, and `draw` puts the result
on screen. Nothing in `scene` draws, and nothing in `filter` knows about a
pipeline.

> A crate per layer was tried, and reverted. It made the layering a compile
> error, which is stronger than a grep — but it also forced every shared item
> to become `pub`, broke every doc link that pointed upward, and bought about
> two seconds of a sixteen-second incremental build. At this size the script is
> the better trade.

For the generated API documentation:

```bash
cargo doc --no-deps --document-private-items --open
```

## Contributing

The two most likely first changes each have a walkthrough:

- [docs/adding-a-filter.md](docs/adding-a-filter.md) — a new way to derive data.
- [docs/adding-an-actor-kind.md](docs/adding-an-actor-kind.md) — a new way to
  draw it.

Longer design arguments live in [docs/design/](docs/design/).

Read [CONTRIBUTING.md](CONTRIBUTING.md) before opening a change. What CI checks:

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
buf lint
```

## Regenerating the protocol code

Rust generates at build time from `proto/`, via
[`build.rs`](build.rs) — nothing to run by hand. The Python bindings are
generated by `buf` and are committed:

```bash
buf generate
```
